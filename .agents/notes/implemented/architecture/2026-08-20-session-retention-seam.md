# Agent Note: Session retention capability seam

Status: implemented

English | [中文](2026-08-20-session-retention-seam.zh.md)

## Problem

Nothing in the harness could delete or expire durable data. Six package READMEs carried the same consumer gap in local words: JSONL logs accumulate until removed externally, SQLite rows accumulate until removed externally, the persistence seam has no deletion API, local spill files persist until external cleanup, the spill seam has no deletion API, and attachment objects are retained indefinitely. `dsh-workspace` names the consumer side of the same hole: session deletion is a separate, absent capability that registration deletion must never substitute for. Deleting one session's durable data therefore required a human to find and remove artifacts in up to three stores by hand, with no cross-store enumeration, no liveness protection, and no per-store outcome reporting.

## Decision

One capability seam, `@deepseek-ai/dsh-session-retention` (`packages/session/session-retention`), owns deletion of one session's durable data across stores.

- **Service Definition + orchestration** — `SessionRetentionRuntime` registers as `ctx.sessionRetention` and owns the vocabulary: a `RetentionParticipant` (one per store, unique `store` label) exposes `plan` (enumerate what a deletion would remove, non-mutating) and `deleteSession` (delete and report). Outcomes are closed unions: a plan is `targets` (possibly empty) or `retains` (the store keeps data by design, with the reason); a deletion is `deleted` (with the removed `RetentionTarget`s), `absent`, or `retained`. The runtime's report adds `failed` for a participant rejection it caught, so one store's failure cannot hide another store's outcome.
- **Consumer surface** — `ctx.sessionRetention.plan(id)` and `ctx.sessionRetention.deleteSession(id)` are the session-management service methods `dsh-workspace` is expected to call; v1 deliberately ships no model-facing tool. `deleteSession` refuses a live session and refuses to run with zero registered participants — an empty fan-out reporting "success" would be a control that cannot fail.
- **Providers** — each store registers through `ctx.inject(['sessionRetention'], …)`, so compositions without the runtime are unaffected. The shared `PersistenceCoordinator` registers one participant per persistence backend over two new OPTIONAL backend hooks, `planStored` and `deleteStored` — optional because an unrelated test fixture (`packages/host/apiproxy`) implements `PersistenceBackend` without them; a backend that omits either simply gets no retention participant. Its `delete` runs on the per-id serialization chain, waits for retirement, refuses live sessions and reserved resume preparations, and drops coordinator caches before the physical delete so a failed backend delete re-derives from disk. The JSONL backend removes the session-owned directory; the SQLite backend deletes the `sessions` row in one transaction and lets `ON DELETE CASCADE` remove its events. `dsh-spill-local` removes its deterministic per-session spill directory. `dsh-attachment-local` registers an honest `retained` participant: objects are content-addressed and deduplicated across sessions, so per-session object deletion is unsafe without reference-aware GC. `dsh-attachment-local` attaches its participant differently: `ctx.on('internal/service', …)` plus `ctx.get('sessionRetention')` inside a plain `ctx.effect`, not `ctx.inject` — this package's own suite-wide test harness (`scripts/test-invariants.ts`) auto-mounts a competing `attachments` fixture on the first `ctx.plugin`-family call made anywhere on a test root, which would deadlock a `ctx.inject`-based registration's own callback under that harness; the `internal/service` event gives the same arrival-order-independent attach behavior without routing through `ctx.plugin`.
- **No automatic policies in v1** — age- and quota-based retention policies are configurable follow-ups; single-session deletion done right is the foundation they will dispatch through.

## Alternatives considered

- **Per-store deletion methods on each existing seam** (a `delete` on `SessionPersistence`, `SpillStore`, `AttachmentStore`) — rejected: every method would have exactly one intended caller (the session-management surface), consumers would have to know every store, and cross-store enumeration/reporting would be reimplemented at each call site. A public service method with one caller is the documented inverse smell.
- **A policy engine first** (age/quota eviction with deletion as an internal detail) — rejected: no current consumer evidence for any default policy, and a policy engine without a correct single-session deletion primitive automates nothing safely. Policies become participants' callers later.
- **Deleting attachment objects by scanning the deleted session's log for references** — rejected: forked and resumed sessions share content-addressed objects, so single-log evidence cannot prove an object unreferenced; deletion there requires store-wide reference counting (deferred), and a wrong guess corrupts other sessions' replay.
- **Registering the persistence participant in each backend package** instead of the shared coordinator — rejected: both backends would duplicate identical registration and liveness logic; the coordinator already owns per-id serialization, retirement, and the caches a delete must drop.
- **A `retention/session-deleted` context event** — deferred, not shipped: no current consumer (projection-cache eviction and the workspace header index would be the first), and an unconsumed event is surface without an owner.

## Consequences

- Bought: one call deletes a session across JSONL/SQLite persistence and local spill storage with per-store outcomes; the workspace surface can wire session deletion without learning store internals; every store's README limitation now points at the seam instead of "external cleanup".
- Cost: `PersistenceBackend` grew two optional hooks; `dsh-session-persistence`, `dsh-spill-local`, and `dsh-attachment-local` now depend on `dsh-session-retention`.
- `dsh-session-persistence-sqlite` and `dsh-storage-sqlite` (`packages/storage/storage-sqlite`) both hand-open a SQLite connection with near-identical `openDatabase(path, journalMode)` steps (`new DatabaseSync`, `PRAGMA foreign_keys`, `PRAGMA journal_mode`, reading and setting `PRAGMA user_version`). This change did not touch either package's open sequence, so the duplication is recorded here, not extracted, as a follow-up for whichever change next touches one of them.
- Attachment bytes are still never reclaimed (`retained` outcome); reference-aware GC remains deferred in `dsh-attachment`/`dsh-attachment-local`.
- Deletion is per-session-id: a forked session's log may reference the parent session's spill locators and attachment objects; deleting the parent leaves the fork's spill references dangling. Lineage-aware deletion is deferred and recorded in the runtime README.
- `dsh-session-projection-cache` rows for a deleted session persist until its own (still deferred) eviction surface exists; they are read only by session id, so they are unreachable garbage, not wrong answers.
- The workspace consumer wiring itself (confirmation UX, folder-removal pairing) remains open in `dsh-workspace`; this seam provides the method it calls.
- An aborted or partially failed `deleteSession` may have deleted some stores and not others; the report says which, and rerunning converges because every participant treats already-deleted data as `absent`.

## Testing

Each provider package tests its own participant end-to-end against real storage (tmp JSONL root, in-memory SQLite, tmp spill root, tmp DSH_HOME) through a real `Context` composition with the runtime; the runtime package tests dispatch, refusal, failure capture, and disposal with controlled participants. `dsh-attachment-local`'s retention tests use direct construction (`new SessionRetentionRuntime(ctx)` / `new LocalAttachmentStore(ctx, …)`), not `ctx.plugin`, for the same test-harness reason as the wiring itself. A scoped per-package coverage run needs `scripts/test-invariants.spec.ts` alongside a touched package's own `tests/` to reach 100% on `src/invariant.ts`: that file's companion only mounts through the suite-wide topology test, not through any package-scoped spec. No keyless snapshot changes: v1 has no model- or product-user-visible output.
