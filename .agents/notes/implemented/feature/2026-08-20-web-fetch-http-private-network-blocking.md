# Agent Note: web-fetch-http blocks private-network destinations by default

Status: implemented

English | [中文](2026-08-20-web-fetch-http-private-network-blocking.zh.md)

## Problem

`dsh-web-fetch-http` fetched any `http(s)` URL a caller supplied with no destination-address check beyond the credential/scheme hygiene `validateFetchUrl` already enforced. Its own module doc and the [web capability seam Agent Note](../architecture/2026-06-24-web-capability-seam.md) named this explicitly: "this provider is an SSRF primitive and must not be enabled in a deployment that can reach sensitive internal network targets." A model with `web_fetch` available could reach `169.254.169.254` (the cloud-instance-metadata endpoint most providers expose to any process on the host), RFC 1918 private ranges, loopback, and other internal-only addresses, and the provider would fetch them exactly like a public page.

## Decision

`HttpFetchProvider` gains a private-network check, `assertPublicDestination`, run against the initial request URL and again against each redirect target before it is followed — not only the first hop, so a same-origin hostname is re-checked even though `isSameOrigin` already refuses a cross-origin one regardless of destination:

- A literal IP hostname (`http://127.0.0.1/`, `http://[::1]/`) is classified directly via `net.isIP`, unwrapping the `[...]` brackets `URL.hostname` keeps around an IPv6 literal.
- A DNS hostname is resolved with `dns.promises.lookup(hostname, { all: true, order: 'verbatim' })`, and every returned address is classified — one private record among several public ones still refuses the request, rather than only checking whichever address a single-result lookup would have returned.
- Classification (`isPrivateNetworkAddress` in `policy.ts`) checks the address against a fixed table of IANA special-purpose ranges via `node:net`'s built-in `BlockList`: RFC 1918 private space, loopback, link-local (which covers the cloud-metadata endpoint), RFC 6598 carrier-grade NAT, IETF protocol assignments, documentation/benchmarking ranges, multicast, and reserved/unspecified space. `BlockList.check(address, 'ipv6')` classifies an IPv4-mapped IPv6 address (`::ffff:10.0.0.5`) by its embedded IPv4 address automatically, so no separate mapped-address rule is needed. These ranges are fixed protocol constants (CLAUDE.md: "Protocol constants, external specs, and security invariants stay fixed"), not configuration.
- A blocked destination throws `WebError` `WEB_BLOCKED_PRIVATE_NETWORK`, naming the resolved address and the requested host.
- A DNS resolution failure (unresolvable host) throws `WEB_PROVIDER_ERROR`, matching how an unresolvable host already failed through `fetch()`'s own network error before this change.

The check is a `Config` field, `blockPrivateNetworks`, defaulting to `true` (schemastery `.default(true)`, the package's existing explicit-default pattern — every other limit here defaults the same way, so no caller can observe an undefaulted field). A deployment that deliberately needs this provider to reach internal targets sets it to `false`. The default being restrictive, rather than requiring an opt-in flag to enable protection, is the point: a `web_fetch`-enabled deployment is protected unless it explicitly opts out, not exposed unless it explicitly opts in.

## Alternatives considered

- **Pin the validated address into the actual connection** (a custom `fetch()` dispatcher/agent whose `lookup` returns only the already-validated address, while still presenting the original hostname for TLS SNI and the `Host` header) — this is what would fully defeat DNS rebinding between validation and connect, and is exactly what the web capability seam Agent Note's original deferred-work entry called for. Not done here: it requires connect-time DNS override plumbing this package has no precedent for (no existing `node:dns`/custom-dispatcher usage in the repo to build on), and the resulting residual gap — a rebind timed into the narrow window between this check and `fetch()`'s own resolution — is materially smaller than the gap this change closes (shipping with zero private-network checking at all). Recorded as the still-open [deferred-work entry](../architecture/2026-06-24-web-capability-seam.md#deferred-work) rather than silently left unmentioned.
- **Hostname-string blocklist only** (matching literal `localhost`/`127.*` strings, no DNS resolution) — rejected: it is defeated by any attacker-controlled DNS name whose A/AAAA record points at a private address, which is the SSRF technique the check exists to stop, not an edge case of it.
- **IP-literal check only, no DNS resolution** — rejected for the same reason; it would satisfy only the literal-IP half of the mission's known-bad list and leave every DNS-hostname-based SSRF vector open.
- **A private-network allowlist of specific hostnames/CIDRs instead of a single on/off switch** — deferred as unrequested surface: no current consumer needs partial access (some internal targets reachable, others not), and CLAUDE.md's "configurability does not justify an unsupported... format... without current-consumer evidence" argues against building it speculatively. A boolean is the minimal config surface the mission's "config-switchable" requirement asked for.
- **A maintained IP-range-checking dependency** (e.g. an npm package for CIDR matching) — rejected in favor of `node:net`'s built-in `BlockList`: it is already maintained (Node core), needs no new supply-chain trust for a security-sensitive check, and the range table itself is a small, fixed, well-documented list this package can own directly.

## Consequences

- `web_fetch` (and any direct `ctx.web.fetch()` caller) refuses `169.254.169.254`, RFC 1918 ranges, loopback (IPv4 and IPv6), and the other IANA special-purpose ranges by default, closing the gap the seam Agent Note flagged as the harness's primary SSRF exposure.
- A deployment relying on this provider to reach internal targets must now set `blockPrivateNetworks: false` explicitly; three existing test suites and two `examples/acp-agent` Cordis configs that deliberately target a loopback fixture server for deterministic, no-external-network testing needed exactly that override (`packages/web/tool-web/tests/integration.spec.ts`, `packages/web/tool-web/tests/spill.spec.ts`, `packages/web/web-fetch-http/tests/fetch-http.spec.ts`'s shared fixture, `examples/acp-agent/web.cordis.yml`, `examples/acp-agent/web.cordis.snapshot.yml`) — none of those are SSRF-relevant behavior, so the override is the correct fix rather than a workaround.
- DNS-rebinding between this check and the real connection remains open (see Alternatives considered); a deployment treating this provider as its complete SSRF defense should read the README's residual-gap disclosure.
- This check's own DNS lookup does not observe the request's timeout/abort signal (`dns.promises.lookup` takes no `AbortSignal`), so a slow or hung resolver can extend a request past its configured `timeoutMs`. Disclosed in the package README rather than solved here — solving it well needs the same connect-time-override plumbing the rebinding gap needs, and is out of this change's scope.
- `tests/fetch-http.spec.ts` covers the mission's literal known-bad destinations (`169.254.169.254`, `127.0.0.1`, an RFC 1918 address, `::1`), a same-origin redirect whose DNS record changes between hops (simulated via a queued `node:dns/promises` mock, since a real rebind is not reproducible deterministically in CI), a resolved-but-private IPv6 record, a DNS resolution failure, the `blockPrivateNetworks: false` bypass, and the restrictive default with no config at all. Package-scoped coverage (`packages/web/web-fetch-http/src`) is 100% statements/branches/functions/lines.
- No model-facing tool schema changed (`web_fetch`'s arguments and result shape are unchanged); the new failure surfaces through the same generic `WebError`-to-structured-tool-error path every other provider error code already uses, so no new snapshot fixture was added for the error text itself. The existing `examples/acp-agent` `web-fetch` snapshot (a success path) continues to pass with the fixture-server override above.
