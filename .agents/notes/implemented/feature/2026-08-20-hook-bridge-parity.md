# Agent Note: closing the four hook-bridge parity TODOs

Status: implemented

English | [中文](2026-08-20-hook-bridge-parity.zh.md)

## Problem

Since [the hook-bridges Agent Note](2026-06-30-hook-bridges.md) shipped, both `dsh-hooks-claude-code` and `dsh-hooks-codex` carried four matched `TODO` markers: `hook-continue-false` (a merged `continue:false` was logged but never halted the run), `session-start-gating` (a SessionStart hook's context raced the first model request instead of being promised to it), `stop-loop-guard` (an unconditionally blocking Stop hook force-continued every step forever, with no cap and a `stop_hook_active` payload field that always reported `false`), and `per-session-hook-config` (only one process-level `configPath` was ever consulted, with no per-session project-local discovery). All four needed identical treatment in both bridges — the same protocol-level primitive, applied at the same extension points, worded only in each dialect's own log prefix.

Two coverage-cases tests (`hooks-claude-code/tests/coverage-cases.ts:418`, `hooks-codex/tests/coverage-cases.ts:397`) asserted the *old* wrong behavior by name — `continue:false` recorded as `"stop"` but the tool still running — as the documented contract of `hook-continue-false` being unimplemented.

## Decision

Five new primitives in `dsh-hook-protocol`, each with a direct per-module unit spec (`tests/halt.spec.ts`, `tests/stop-guard.spec.ts`, `tests/start-gate.spec.ts`, `tests/session-config.spec.ts`, `tests/config-limits.spec.ts`), imported symmetrically by both bridges:

- **`applyHaltRequest(merged, point, agent)`** (`src/halt.ts`) maps a merged `continue:false` onto `agent.cancel({ kind: 'hook', reason })` — `reason` is the first halting hook's `stopReason`, falling back to a point-named string. Both bridges call it at `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, and `Stop` whenever `merged.stop`; `SessionStart`/`SubagentStart`/`SubagentStop` still have no open turn to halt, so `continue:false` there remains neither recorded nor honored (unchanged, and now stated explicitly in both READMEs rather than left implicit).
- **`createStopLoopGuard(max)`** (`src/stop-guard.ts`) counts consecutive forced continuations per `(agent, turn)`. `agent.steer()` sends to the `'next-step'` inbox target, not `'next-turn'` — verified empirically (both `hook/invoked` records for a two-block Stop test land on turn 1) — so keying the cap on `turn` is correct: steering never opens a new turn out from under the counter. `stopHookActive(agent, turn)` now backs the payload's `stop_hook_active` field truthfully; `tryForceContinue` refuses once `max` is reached (default `DEFAULT_MAX_CONSECUTIVE_STOP_BLOCKS = 8`, Claude Code's own guard threshold, which Codex's bridge borrows since Codex documents no cap of its own) and the bridge lets the turn stop instead of steering again.
- **`createStartGate()` / `bindStartContext(gate, agent, inject)` / `foldStartContext(inject, startContext, decision)`** (`src/start-gate.ts`) replace the old "detached hook resolves, `agent.inject()` whenever it does" pattern. The bridge's first `agent/pre-step` listener calls `bindStartContext`, which claims the agent's pending SessionStart run (registered synchronously inside `agentLoop.create()`, before `followup()` can even run) and awaits it, then returns a folder: an entering `PreStepDecision` gets the context appended to its messages, a non-entering one gets it injected directly (parked for the next wake). This converts a race into a bounded stall on the hook's own timeout — an immediately-sent first prompt now reliably carries the SessionStart context on its *first* request, proven by rewriting the CC bridge's "SessionStart timing is best-effort (no-wait)" test into an assertion that `adapter.requests[0]` contains the hook's context (a third behavior-change test beyond the two the mission named, called out here since a reviewer diffing against the brief would otherwise flag it as unaccounted for). `StartGate.register`'s rejection path (a `run` that itself rejects, as opposed to a `deliver`/`agent.inject` that throws) is contained inside `register` via a caller-supplied `onError`, not the bridge's own `.catch` — see Alternatives.
- **`loadProcessHookConfig(opts)` / `createSessionHookConfigCache(opts)` / `combineHookGroups(processGroups, sessionGroups)`** (`src/session-config.ts`) implement the new `Config.sessionConfigFile?: string` field both bridges added. `loadProcessHookConfig` keeps the existing "read/parse failure ⇒ warn + register nothing" behavior when `sessionConfigFile` is unset, and degrades to "warn + keep running on session-local discovery alone" when it is set. `createSessionHookConfigCache` returns a per-agent lookup, reading and parsing a workspace-relative file once per session at first hook use (ENOENT is silent; any other error warns with the path and agent id) and caching the result — including "no file"/"no cwd" — keyed weakly by a structural `SessionWorkspace` (`{ id, session: { header: { cwd? } } }`) so this library does not depend on `@deepseek-ai/dsh-agent`. `combineHookGroups` concatenates one point's process-level and session-level matcher groups, session groups running after process groups, at every `runPoint` call.
- **`resolveSharedHookLimits(bridge, config)` / `assertPositiveInteger(bridge, name, value)`** (`src/config-limits.ts`) default and validate the new `maxConsecutiveStopBlocks` field alongside the pre-existing `stderrSummaryMaxChars`, before any config-file parsing, so a bad value cannot be hidden by a load failure's early return.

`HookOutput.updatedInput` stays unhonored: `PreToolDecision` in `packages/core/tools/src/index.ts` is a closed `allow | deny | ask` union with no rewrite kind, so honoring it needs a `packages/core/tools` change, out of this lane's `packages/hooks/*` ownership. The finding is not new — it was already recorded at [the pre-tool-input-rewrite Agent Note](../../proposed/feature/2026-06-30-pre-tool-input-rewrite.md) and cited from both bridge READMEs — so this note does not duplicate it, only confirms the constraint still holds.

The two coverage-cases tests documenting the old behavior were rewritten to assert the new one: a `{"continue":false}` `PreToolUse` hook now denies the tool (it never runs) and the turn ends `{ kind: 'aborted', reason: { kind: 'hook', reason: 'halt' } }`, instead of the tool running and the turn completing normally.

## Alternatives considered

**Wrapping the twin bridges' new near-identical code in `jscpd:ignore` markers** instead of extracting it. The duplication gate (`pnpm run duplication`) flagged three fresh clones after the twin TODO fixes landed — the config-loading/session-discovery control flow, the matcher-group merge, and the pre-step start-context binding. Genuine extraction (the five primitives above) resolved all but a residual 10-line/66-token span of pure `ctx.on()` registration boilerplate around the now-trivial `bindStartContext` call, which was folded into `hooks-codex`'s pre-existing `jscpd:ignore` span (already used there for the identical category of "shared-helper call site, dialect differences begin after this point") rather than opening a new one — consistent with existing precedent, not a new exemption.

**Reporting `StartGate.register`'s run-rejection at the bridge, not the library.** The prior code had one `.catch` spanning `runPoint(...).then(agent.inject).catch(warn)`; splitting delivery into `register`'s internal `deliver` call made the inner half of that chain (`run` itself rejecting, as opposed to `deliver` throwing) structurally unreachable through any bridge-level test, because `runHook` is documented to never throw and `appendHookInvoked`/`appendHookResult` are gated off for the turn-less SessionStart point. That inner catch was also not merely dead: an uncontained `run` rejection would leave a `claim()` returning a promise the caller must inherit as a rejection, defeating `bindStartContext`'s "must not reject" contract from the caller's side. Moving the rejection→`undefined` conversion into `StartGate.register` itself (a caller-supplied `onError`) restored full reachability (`start-gate.spec.ts` exercises it directly with `Promise.reject`) and kept the invariant enforced at its owning layer instead of duplicated per bridge.

**Keying the Stop-loop cap on the run instead of the turn.** Considered because a forced continuation could in principle open a new turn, which would silently reset the counter and make the cap vacuous. Verified empirically first (see Decision) that `agent.steer()` stays within the same turn, so turn-keyed accounting is correct as designed; no change was needed.

## Consequences

`packages/hooks/hook-protocol/src/**`, `hooks-claude-code/src/**`, and `hooks-codex/src/**` are at 100% per-file statement/branch/function/line coverage (`node node_modules/vitest/vitest.mjs run packages/hooks --coverage --coverage.include='packages/hooks/*/src/**'`), `pnpm run duplication` reports zero clones, and `pnpm run typecheck` / `pnpm run lint` are clean. Both bridges' `Config` gained `sessionConfigFile?: string` and `maxConsecutiveStopBlocks?: number`; both README "Known Limitations" sections lost their `TODO(hook-continue-false)` / `TODO(session-start-gating)` / `TODO(stop-loop-guard)` / `TODO(per-session-hook-config)` markers and gained accurate replacement prose, including the `hook-protocol` README's own primitives table and the previously-stale "SessionStart context parks in the inbox" line. A future third dialect bridge gets the same four behaviors by importing the same five `dsh-hook-protocol` exports rather than re-deriving them.
