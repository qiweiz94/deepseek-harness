# Agent Note：诊断筛选插件

状态：已实现

[English](2026-08-20-diagnostic-sifter-plugin.md) | 中文

## 问题

把仓库自身的类型检查或范围化测试运行作为一次工具调用来执行，返回的是原始的 `tsc -b`/`vitest run` 输出：一个被破坏的导出可能级联出几十行下游的 `TS2307`/`TS2724` 错误，一次失败的测试运行会把通过测试的噪声、代码帧与堆栈跟踪，和唯一真正失败的那条断言混在一起。消费这种输出的模型要么白白耗费上下文重新阅读它无法采取行动的级联噪声，要么一个盲目截断的调用方会把一个真实的、可解释的失败变得与静默损坏的解析器无法区分。

## 决策

**新增面向模型的插件 `@deepseek-ai/dsh-plugin-diagnostic-sifter`，注册一个 `run_diagnostic_check` 工具**，通过 `ctx.subprocess`（argv、cwd、超时都是 `Config` 字段，绝不是硬编码的调节项）派生配置好的 `tsc -b --pretty false` 构建或 `vitest run`，只返回根因诊断。

**级联抑制是有针对性的，而非全局的。** `TS2307`/`TS2724` 诊断的消息中携带它们引用的模块说明符；只有当该说明符（按 basename）能对应到本次运行中**也**有自身保留诊断的文件时，这一诊断才会被抑制。一个真正缺失的模块引发的 `TS2307`——在运行中没有匹配的保留诊断——仍会保留为根因。（早期草稿只要运行中存在任何其他诊断，就会抑制全部 `TS2307`/`TS2724`，这会静默丢弃真正独立的、缺失模块导致的错误；`tests/fixtures/tsc-failing.txt` 下真实捕获的 fixture 在上线前暴露了这个问题。）

**解析失败的判定基于包络处理之前的筛选结果，而非之后的。** 在极小的 `maxOutputBytes` 下，`boundRootCauses` 可以合理地把一个非空的 `rootCauses` 列表收缩至接近空——这是包络截断（`truncated: true`），不是无法解析的运行。`parseFailure` 由筛选器自身在有界化之前的 `recognized`/`rootCauses` 结果计算得出，因此极小的包络只会截断，绝不会被误报为"无法解析此输出"。

**流捕获、根因列表与解析失败时的原始回退三者共享同一个 `maxOutputBytes`**，都经过 `@deepseek-ai/dsh-output-retention` 的 `TextRetainer`（`head` 策略），因此工具在任何阶段都不会缓存超过包络允许的内容。派生进程的环境固定设置 `NO_COLOR=1`（这是为筛选器纯 ASCII 正则表达式做的协议卫生措施，不是一个可部署调节的选项），因为启动期失败（例如无法解析的 vitest 配置）由 Vite 自身的报告器格式化，它无条件地上色，不受 TTY 影响。

**筛选逻辑是纯函数，并针对真实捕获的输出做了单元测试。** `src/sifter.ts` 中的 `siftTypecheck`/`siftTest`/`boundRootCauses`/`retainRaw` 不接收 `ctx`，也不做任何 I/O；`tests/fixtures/*.txt` 是真实的 `tsc --pretty false`/`vitest run` 输出（TypeScript 6.0.3、vitest 4.1.8、`NO_COLOR=1`，管道写入文件——而非手写），一次捕获、重复回放，合成字符串仅用于真实捕获难以可靠复现的边界分支（去重、无法识别的级联目标、精确/极小/多字节的字节预算）。

## 备选方案

**只要运行中存在任何其他诊断，就抑制全部 `TS2307`/`TS2724`。** 已否决（见"决策"）：这会把"真正下游于某个破坏"和"恰好共享一个模块解析失败代码"混为一谈，导致独立损坏的导入从模型视野中消失。

**用有界化之后（`maxOutputBytes` 处理之后）的根因列表来计算 `parseFailure`。** 已否决：这会让包络大小与解析失败判定变成同一个信号，导致包络较小的调用方对本来解析得很好的运行看到错误的"无法解析此输出"报告。

**让 `tsc`/`vitest` 自身的 TTY 检测来处理颜色。** 对派生进程的环境已否决：经验证 vitest 自身的报告器确实会遵从非 TTY 管道，但配置加载失败由 Vite 独立的错误格式化器渲染，它并不遵从——`NO_COLOR=1` 无条件地补上这个缺口，而不是依赖一个只在部分路径上才做检查的代码路径。

## 后果

加载该插件的组合会暴露一个 `run_diagnostic_check` 动词，把仓库的类型检查或测试运行变成一个有界的、仅含根因的诊断列表，级联抑制与截断各自通过独立字段报告，而不是被塌缩成单一、含糊的失败状态。误配置（空的 `tscArgs`）在 `apply` 处大声失败。`tsc -b` 要求目标 `tsconfig.json` 是 composite/solution 项目；非默认的 vitest 报告器不会被解析器识别，会表现为响亮的 `parseFailure` 而非静默的干净结果——这两者都是已记录、留待后续的限制，而非工具代替调用方纠正的内容。
