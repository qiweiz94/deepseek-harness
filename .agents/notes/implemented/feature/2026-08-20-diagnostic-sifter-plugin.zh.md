# Agent Note：诊断筛滤插件

状态：已实现

[English](2026-08-20-diagnostic-sifter-plugin.md) | 中文

## 问题

模型若通过 shell 工具运行项目的类型检查或测试套件，就得读完整份输出才能找到缺陷。这份输出大部分是它必须付 token 的噪声：一个无法解析的模块会在每个 import 处被报告，一个改名的导出会在每个使用处被报告，失败的测试运行还会打印所有通过的用例，以及定位测试运行器而非缺陷的栈帧。真正的信号——究竟哪几条诊断解释了这次失败——被埋没了，而且失败越大，占用的上下文越不成比例。

## 决策

**新增面向模型的插件 `@deepseek-ai/dsh-plugin-diagnostic-sifter`，注册一个 `run_diagnostic_check` 工具**，接受 `command` 枚举（`typecheck` 或 `test`）与可选的 `targetPath`。它启动该命令所配置的可执行文件——默认为 `node_modules/.bin/tsc -b` 与 `node_modules/.bin/vitest run`——并返回 `{ success, rootCauses, suppressedCascadeCount }`，而不是原始输出。

**级联折叠回其原因。** 代码与文本重复的诊断折叠到首次出现处。模块解析与导出形态类代码（`TS2307`、`TS2305`、`TS2503`、`TS2614`、`TS2688`、`TS2724`）按代码加第一段引号内主体折叠，因为结尾的 "Did you mean" 提示逐个 import 处不同，而原因相同。分组按其波及的位置数排序，因此最宽的级联——最可能的原因——排在最前，`maxRootCauses`（默认 3）限定报告条数。`suppressedCascadeCount` 说明模型没有看到多少条已解析的诊断，因此省略绝不是无声的。

**结果被两次限界。** 两个子进程流都经 `@deepseek-ai/dsh-output-retention` 的 `TextRetainer`（`head` 策略）在 `maxOutputBytes`（默认 15 KB）处保留，因此即使编译器输出数 MB，内存中也不会超过包络；头部正是诊断所在。随后返回值被拟合到 `maxResultBytes`（默认 1,000）：先沿固定的码点阶梯截断消息，只有仍不够时才把排名最低的根因丢入被抑制计数。

**失败总会指名某个东西。** 非零退出若未匹配任何诊断模式，仍返回一条编码为 `nonzero-exit` 的根因，携带第一行非空输出，因此无法识别的 reporter 只会退化为单薄的回答，而不是一个读起来像成功的空列表。

**所有进程都经过 `ctx.subprocess`。** 插件只负责编排、解析与排序。配置为相对路径的可执行文件在启动前锚定到 `cwd`，因为 Node 按父进程而非子进程的工作目录解析相对可执行路径；`targetPath` 始终是独立的 argv 项，不经过任何 shell 解释。

## 备选方案

**让模型调用现有的 bash 工具并阅读原始输出。** 已否决：这正是本 Note 所针对的 token 成本现状，而且 bash 工具的字节包络截断的是尾部，而编译器的错误计数与测试运行器的失败用例段恰恰在那里。

**返回经正则过滤的原始输出。** 已否决：过滤去掉的是行，不是级联——同一个缺失模块错误的四十份副本会原样通过过滤，模型仍要自己推断它们是同一个缺陷。

**解析机器可读的 reporter（`tsc --pretty false` JSON、Vitest 的 JSON reporter）。** v1 否决：两者都不是仓库自身配置的脚本所产生的输出，工具会与开发者看到的内容悄然不一致，而且 Vitest 的 JSON reporter 需要输出文件。文本解析器作为限制被记录在案，将来有消费者需要时可再补一条 JSON 路径。

**把 `suppressedCascadeCount` 只算作级联重复，不含被上限截掉的根因。** 已否决：紧凑结果放不下两个数字，而一个不含上限截断的计数会让报告看起来完整、实则不然。单个数字覆盖所有未列出的已解析诊断。

## 后果

加载该插件的组合会暴露一个 `run_diagnostic_check` 动词，其回答无论失败多大都是有界的：整仓构建中断与单个坏文件对模型的 token 量级相同。配置错误（非正的 `maxResultBytes`、`maxOutputBytes`、`maxRootCauses` 或 `timeoutMs`）在加载时大声失败。由于每次调用拥有互不相交的进程树且不写入任何仓库状态，该工具是并发安全的。

解析器识别 `tsc`（普通与 `--pretty`）与 Vitest 默认 reporter；其他编译器或运行器会退化为单条 `nonzero-exit` 根因。级联分组是启发式的，因此两个产生逐字节相同诊断的独立缺陷会算作一条根因、另一条被抑制——计数始终会说明这一点。相关信息行、源码摘录与断言 diff 被丢弃，因此含义依赖摘录的根因会比原始输出更单薄。v1 仅前台、仅本地进程；后台试运行、远程执行与自动应用建议修复仍待后续。
