# Agent Note: 设置持久化关闭五处正确性缺口，并获得持久化原子写入

Status: implemented

[English](2026-08-20-settings-persistence-correctness-and-durability.md) | 中文

## 问题

`@deepseek-ai/dsh-settings` 及其共用的 `@deepseek-ai/dsh-atomic-write` 原语存在五个未关闭的 `TODO`，外加一处持久性缺口；每一个都可能在从不大声报错的情况下损坏或泄露设置状态：

- **原型形态键**（`settings-json-properties`）：`cloneJsonShaped`、`mergeLayers`、`applyPathOp`、`deepEqualJson` 与脱敏遍历器通过普通属性访问来读写动态键。解析后的文档段落若以 `"__proto__"` 为键，该键不会作为数据存活——赋值会重新为正在构建的对象设置原型，而不是存入该键——并且通过一个不存在的 `"__proto__"` 路径执行 unset 时，会把 `Object.prototype` 当作子段落读出。
- **观察者静默**（`settings-registration-quiescence`）：注册方 fiber 销毁时不会排空其观察者回调。一次已经在途的观察调用，或在销毁前一刻刚排入队列的调用，仍可能在注册方的销毁器已经返回*之后*运行——或仍在运行——导致销毁器返回之后的下游代码在本应确认"该 fiber 已消失"时依旧观察到一次回调。
- **替换重同步**（`settings-replacement-resync`）：当某次写入仍在进行时注册方被替换，替换注册的解析值仍是写入前从旧文档读出的那份。该次写入自己持久化的段落会被替换视图静默丢弃，直到下一次无关写入恰好把它刷新为止。
- **线路脱敏**（`settings-wire-redaction`）：`redactSecrets` 只遍历 `object`/`dict`/`array` 三种 schema 节点。若某个 `role('secret')` 字段只能通过 `union`、`intersect`、`transform` 或 `tuple` 节点到达，此前会被原样返回，且没有任何记录表明遍历器遗漏了它——schema 作者可能以为该字段已被脱敏，实际并未脱敏。
- **命名空间用词**（`settings-namespace-vocabulary`，本次保持未关闭）：`SettingsDescriptor.ns` 早于公共 API 其余部分已经确立的 `namespace` 用词。该字段线路可见（`dsh-host-apiproxy` 的 RPC 接口中的 `SettingsNamespaceView` 与写请求负载），并被六个以上的 `dsh-client-*` 包直接读取，还出现在生成的 `gen-cordis-api` 目录中 `SettingsDescriptor` 的条目里。一次干净的重命名需要将这些包与本包一并纳入同一变更；见"考虑过的替代方案"。
- **原子写入持久性**：`writeFileAtomic` 提交 rename 时既不对临时文件的内容做 `fsync`，也不对父目录项做 `fsync`，因此一次成功的 `rename()` 与操作系统真正把两者之一落盘之间若发生崩溃，即便每个观察到该 rename 的读取方都已经看到完整内容，替换仍可能被回退。

## 决定

**自有属性键。** 四个变更类辅助函数与脱敏遍历器现在对每一处"文档提供的字符串将成为属性键"的场景，一律使用 `Object.hasOwn` 做存在性判断、用 `Object.defineProperty(..., { enumerable: true, writable: true, configurable: true })` 做写入，取代 `in`/中括号赋值。此后，`"__proto__"`、`"constructor"`、`"__defineGetter__"` 之类的键与任何其他字符串键别无二致：它们会被正常克隆、合并、打补丁、比较与脱敏，并且绝不可能重新为正在构建的对象字面量设置原型或做出其他变更。

**销毁时排空。** 注册 effect 的销毁器现在会先停用注册方的每一个活跃观察者，再返回；并等待每个观察者已经开始的调用尾部完成。到销毁解析完成时，一次调用要么已经完整结束，要么根本没有开始过；没有任何调用会横跨这条边界。

**从已持久化段落重新解析。** 某次写入在其注册方被替换的同时完成提交时，现在会从*刚刚持久化*的文档段落——而不是替换注册最初针对的那份文档快照——重新解析替换注册，提升其修订号，并从该次解析结果发布，而不是让替换注册停留在写入前的旧文档上。若替换注册的 schema 或 `validate` 拒绝该已持久化段落，则保留替换注册的最后一个良好值并发出警告，与普通发布路径完全一致；不存在"替换发生在写入过程中"这一单独的降级分支。

**对不可达的密钥失败关闭。** `redactSecrets` 的遍历器新增了 `declaresSecret` 子树检查与 `guardMismatch` 兜底。此后，任何遍历器在结构上不会遍历的节点（`union`、`intersect`、`transform`、`tuple`，以及未来任何新增的节点种类）——只要其下方任意位置声明了 `role('secret')` 字段——都会抛出异常，并在错误信息中指出那条不可达路径：遍历器无法在这种形状内部定位该密钥，因此拒绝脱敏，而不是把值原样放行。另外，当某个节点是 `object`/`dict`/`array`，但运行时值的形状与之不匹配时（例如声明为数组、实际却是记录），该值会被剥离，其容器位置会被记录进 `secrets`，而不是原样放行：遍历器同样无法深入这种形状不匹配的情况，因此叶子处适用与"不支持的节点种类"完全相同的失败关闭规则。对于未声明任何密钥的 schema，两种情况都保持此前的原样放行行为——新增检查在没有需要保护的内容时不会触发。

**持久化的原子写入。** `writeFileAtomic` 现在直接用 `open(temp, 'wx', mode)` 打开临时同级文件，而不是使用一次性的 `writeFile` 辅助函数；写入内容后、在关闭并 rename 之前调用 `handle.sync()`。同步失败会像此前写入失败时一样中止该次写入（移除临时文件、重新抛出错误），因此崩溃绝不会让设备从未收到的内容变成正式内容。rename 提交之后，新增的 `fsyncParentDirectoryBestEffort` 辅助函数会以只读方式打开父目录并对其做 fsync，但与内容 fsync 不同，它会同时吞掉 open 与 sync 两处的失败，而不是向外传播：此时 rename 已经把新内容提交到了其最终文件名下，因此目录项持久性失败并不会改变该次写入是否成功，只会影响后续一次崩溃恢复能多快观察到它。`withFileLock` 的锁文件写入未受影响：它不需要内容持久性，只需要既有的 `wx` 独占性。

## 考虑过的替代方案

- **命名空间用词——本次就完成重命名。** 已拒绝：该字段线路可见，其消费方横跨 `dsh-host-apiproxy` 的通用 RPC 处理、生成的 `dsh-tool-cordis` API 目录，以及六个以上的 `dsh-client-*` 包，均不在本次变更的所有权范围内。在此改动这些文件可能触及另一条并行车道正在持有的文件，也会把一次无关的重命名混入一次以正确性与持久性为主题的 PR。`TODO` 予以保留，现在补充记录了完整的消费方清单，以便后续的跨包专项变更可以直接承接，而不必重新摸排范围。
- **原型形态键——改在文档边界处对 `"__proto__"` 做清洗/拒绝。** 已拒绝：文档作者选用 `"__proto__"` 作为命名空间内部键虽然不常见，但仍是合法的 JSON；若加以拒绝，会让存储的行为依赖一份需要随每次新发现的危险键而持续更新的黑名单。自有属性访问一次性关闭了整类问题（任何与 `Object.prototype` 成员冲突的键），无需枚举。
- **观察者静默——让在途调用与销毁竞速，由调用方自行检查存活状态。** 已拒绝：这会把一项正确性要求（在处理回调前先检查 `hasSettled`）推给当前及未来的每一个观察者，而"销毁之后不再有回调"这一保证本可以由注册表集中提供一次即可。
- **替换重同步——只在下一次无关写入时才重新发布。** 已拒绝：这会留下一个长度不定的窗口（直到*某个别的写入*发生为止），在此期间替换注册的解析值会与已持久化文档静默不一致，且没有任何信号表明存在一次待处理的重同步。
- **线路脱敏——枚举所有可能出现的 schema 节点种类，为 `union`/`intersect`/`tuple` 添加容器支持。** 推迟而非彻底拒绝：为这些节点种类提供完整的遍历支持是一项更大的 schema 遍历改动，有其自身的设计空间（当只知道运行时的值时，该值究竟属于哪个 union 分支？）。本次的失败关闭把一次静默泄露转化为一次响亮的、可在注册时或写入时修复的错误，这正是本次变更需要的正确性属性；更完整的遍历支持仍是尚未完成的后续工作。
- **原子写入持久性——像 `dsh-storage-json` 的 `writeAtomic` 一样，对目录 fsync 也失败关闭。** 针对这一共用原语专门拒绝：`dsh-storage-json` 的后端每个进程恰好只有一个写入方，可以承受在目录 fsync 失败时让整次写入直接失败。而 `dsh-atomic-write` 被用户设置文档与凭据存储共用，运行在任意宿主文件系统（包括网络挂载）与平台之上（Windows 无法像本辅助函数这样以只读方式打开目录）；仅因为*目录项* fsync——一项缩小崩溃恢复窗口的改进，而非正确性要求——未能完成就让整次写入失败，会在最不能承受写入失败的那些文件系统上，把一个本不影响可用性的问题变成一次写入失败。内容 fsync 之所以保持失败关闭，是因为它的失败确实意味着数据可能尚未写入。
- **原子写入持久性——在 `writeFile` 之后重新打开临时文件，而不是改用 `open`+`handle.sync()`。** 已拒绝：这会多出一次不必要的 open/close 往返，而当前实现已经从最初的 `wx` 创建起就持有着打开的句柄，没有必要额外往返。

## 后果

- 设置文档段落、凭据存储记录或路径操作的目标可以使用任意字符串键，包括与 `Object.prototype` 成员冲突的键，而不会污染正在构建的对象，也不会把原型属性当作已存储的数据暴露出来。
- 已销毁的注册方的观察者可被证明已经静默：`tests/settings.spec.ts` 会在一次调用进行中销毁 fiber，并断言此后不再有回调运行，且销毁器要等到该在途调用结束后才会解析。
- 在一次写入仍在进行时被替换的注册方，此后在下一次读取时始终从该次写入已持久化的段落重新解析，其结果与"替换在写入开始前就已注册"时发布出来的结果一致。
- 若某个密钥 schema 配置有误（`role('secret')` 字段位于遍历器无法遍历的节点种类之后），此后会使注册或对应写入直接失败，错误信息中指明那条不可达路径，而不再是静默地把密钥的值发送到线路上。`tests/redact.spec.ts` 针对 union/intersect/tuple 场景、一个结构上无类型的节点（当前任何 schemastery 构造都不会产生这种节点，但遍历器的结构化 `SchemaNode` 约定并未将其排除在外），以及 object/dict/array 形状不匹配场景，作为已知错误输入进行了验证。
- `writeFileAtomic` 的调用方无需改动 API 即可获得默认的崩溃持久内容：此前从未收到 fsync 字节的设备，现在会表现为一次被拒绝的写入，而不是一次在下次崩溃时静默回退的 rename。`dsh-atomic-write/tests/atomic-write.spec.ts` 通过对 `FileHandle.prototype.sync` 打桩与对 `node:fs/promises` 的 `open` 做模拟，分别强制触发一次内容 fsync 失败（写入被拒绝、临时文件被移除、目标文件不存在）以及一次目录 open 失败与一次目录 fsync 失败（两者均正常解析，目标文件持有新内容）。既有的 `dsh-settings-file`/`dsh-credentials-local` 真实组合测试套件也相应更新，把此前模拟的临时写入失败改为通过 `open()` 注入，因为不再调用 `writeFile()`。
- 命名空间用词的重命名仍保持未关闭，现在其消费方清单已记录在源码注释中，后续变更无需重新摸排。
- `dsh-settings` 自身范围内的测试套件已能独立达到该包按文件计的 100% 覆盖率门槛：`installSettingsSection` 的 `validate` 钩子转发分支与 `redactSecrets` 的无类型节点分支早于本次变更就已存在（自线路脱敏与观察者静默两处修复落地起即存在），但此前没有直接测试；两者现在都被直接覆盖，不再依赖跨包间接触发。
