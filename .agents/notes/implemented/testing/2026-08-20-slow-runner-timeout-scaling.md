# Agent Note: Slow-runner test-timeout scaling

Status: implemented

English | [中文](2026-08-20-slow-runner-timeout-scaling.zh.md)

## Problem

The first Fork CI run (32333218317) failed six tests on wall clock rather than behavior: the fork's hosted lanes run on 4-core `ubuntu-latest` while every timeout in the repository was tuned on faster development machines and upstream's 16-core pools. `scripts/oxlint-contract.spec.ts` lost three tests at the 5s vitest default (actual 6-9s), `packages/core/tools/tests/py-types.spec.ts:937` and `packages/client/ui-primitives/tests/code-block.client.spec.tsx:44` overran the same default by ~1.3x, `packages/typert/generator/tests/tools-catalog.spec.ts:20` hit its explicit `{ timeout: 30_000 }` at 37.8s, and the acp `subagent-continuable-inheritance` scenario exhausted the snapshot harness's hardcoded 10s persistence-wait bound. Separately, the `pwsh-tool-turn` pinned header (issue #24) diverged on Linux: its `tool-schemas.expected.json` predated the tool-jobs task-to-job wording rename and the sandbox-denial sentence added to the pwsh tool description — staleness invisible locally because the scenario self-skips on pwsh-less development hosts, and the ubuntu runners ship pwsh.

## Decision

`vitest.shared.ts` exports `testTimeoutFactor()` and `scaledTimeout(baseMs)`, reading `DSH_TEST_TIMEOUT_FACTOR`: unset or empty means 1 (every bound exactly as authored); a set value must parse as a finite number >= 1 or the caller throws. `vitest.config.ts` routes vitest's own 5s default through `scaledTimeout(5_000)` at the root and in both projects. Two consumers cannot import that root module and carry the identical small validation locally instead, each for a distinct compile-boundary reason: the acp-snapshot harness's `packages/test-support/acp-snapshot/src/harness.ts` exports its own `waitTimeoutFactor()` (package source under `rootDir: src` cannot import a repository-root config module) and computes `defaultWaitTimeoutMs()` per call — a default-parameter expression evaluated fresh on every wait a scenario issues, which also makes `waitTimeoutFactor()` directly unit-testable without module-reset tricks; `packages/typert/generator/tests/tools-catalog.spec.ts` carries a local `scaledTimeout(baseMs)` because that test file compiles under `tsconfig.host.json`, whose explicit file list (and its stricter `exactOptionalPropertyTypes`) cannot reach a repository-root module — importing `vitest.shared.ts` there failed `tsc -b tsconfig.host.json` with a TS6307 project-file-list error, not just a runtime one. `fork-ci.yml` sets factor `4` in the coverage lane and `8` in the consumers lane — the largest measured overrun ratio outside the acp `subagent-continuable-inheritance` scenario is ~1.3x, but that scenario spawns multiple real agent subprocesses that compete for the same 4 cores as the concurrently-running snapshot scenarios (`DSH_SNAPSHOT_MAX_CONCURRENCY: '4'`); a live PR run measured factor 4 (40s scaled bound) insufficient for it, so consumers moved to 8 as a first widening — not a bound confirmed sufficient by measurement, only confirmed necessary to exceed 4. The stale `pwsh-tool-turn` sidecar was regenerated keylessly (`DSH_SNAPSHOT=refresh`, scoped to the scenario) on a macOS host with pwsh installed; the resulting diff is tool-description text plus a tool-order change (`pwsh` moves from first to last), carries no paths or platform content, and the refreshed replay passes from one recording on the fast-forwarded tree (post PR #26). `ToolRegistry.schemas()` (`packages/core/tools/src/index.ts:1234`) projects visible tools in `Map` insertion order with no sort anywhere in the registry or normalizer, so tool order in the pinned header is genuinely registration-order-dependent — the new order was verified deterministic (7 runs against the regenerated golden, 2 of them under deliberate all-cores CPU stress, identical order every time) and matches `examples/acp-agent/tests/pwsh.cordis.yml`'s actual declaration sequence (`tool-pwsh` is the last top-level entry, mounted after `acp-agent` pulls in `tool-jobs`'s `job_kill`/`job_output`); the previously-committed golden's `pwsh`-first order was the stale one. There is no probe with a timeout anywhere in `tool-pwsh`'s or `pwsh-local`'s registration path on non-Windows — `resolvePwshPath()` (`packages/shell/pwsh-local/src/resolve.ts`) returns the literal string `'pwsh'` with zero I/O off Windows, and both packages' `apply()`/constructor are synchronous — so a registration-race explanation for either the order or a missing-tool report was investigated and not supported by the registration code or by repeated stressed runs.

## Alternatives considered

- An absolute `DSH_TEST_TIMEOUT_MS` override (issue #23's sketch): a single absolute value cannot reach explicit per-test bounds like tools-catalog's 30s without erasing their authored proportions, and it either starves long suites or balloons short ones. A factor preserves each bound's meaning.
- Raising the defaults for every environment: loosens locally-run timeouts and hides regressions on fast machines; the issue forbids it.
- Re-recording the pwsh fixtures per platform: the divergence was fixture staleness, not platform-dependent content — a refresh on any pwsh-bearing host reproduces byte-identical text, so one recording still serves every platform.
- A module-load constant for the harness's default wait timeout (the first draft): computed once via an IIFE at import time, its throw branch could only be exercised by resetting the module cache and re-importing under a bad environment value, which is workable but heavier than necessary; a per-call function makes the same validation directly unit-testable and needs no module-reset gymnastics in `harness.spec.ts`'s `waitTimeoutFactor` suite.

## Consequences

- The CI lanes tolerate 4x (coverage) or 8x (consumers) wall clock per test and per persistence wait; a garbage factor fails the run loudly — at `vitest.shared.ts`/`tools-catalog.spec.ts` config evaluation, or the first unscaled wait a harness scenario issues — instead of silently running unscaled.
- Bounds not routed through the factor stay unscaled. Known instances: the `expect.poll` 10s bound inside `apps/web/tests/chat-scroll-contract.e2e.ts` and any other spec-local literal; they need their own adoption if their lanes keep flaking.
- `pwsh-tool-turn` replays on macOS and Linux from one recording again. Future model-visible wording changes in tool-jobs or tool-pwsh will fail this pinned header on any pwsh-bearing host — that detection is the point of the pin; refresh the sidecar in the same change.
- `scaledTimeout`'s small validation now has three copies (`vitest.shared.ts`, `harness.ts`, `tools-catalog.spec.ts`), each pinned to a distinct compile-project boundary that forbids importing the root module. Extracting a fourth shared copy would need a package both `tsconfig.host.json` and every consuming project's `tsconfig` can reach — no current package fits without becoming a build-tooling dependency of product source, so the duplication stands until one does.
- Investigating issue #24's `apps/web` fixtures surfaced two further failures NOT fixed in this change: `apps/web/tests/minimal-preset.snapshot.ts` and `apps/web/tests/shipped-composition.e2e.ts:84` both reject `get_file_outline`/`get_directory_outline` appearing on the pre-agent, no-preset-mounted `ctx.tools.schemas()` — a documented invariant ("the global layer holds nothing"), not simple snapshot staleness alongside the pwsh-tool-turn case. Sibling base-bundle entries in the same `packages/bundle/base/cordis.patch.yml` block (`tool-goal`, `tool-todo`, `tool-ralph`) do not leak into that pre-mount scope; `plugin-ast-context`'s own `apply()` uses the identical `ctx.tools.register` pattern as those siblings, so the asymmetry was not resolved to a specific line. Likely introduced by `0a78be1a48` (`feat(wiring): ship ast-context plugin in base bundle`, landed on master before this run), which touched only `packages/bundle/base/cordis.patch.yml` and the headless example, not these `apps/web` tests. Left unfixed here: `packages/bundle/base/cordis.patch.yml` is outside this change's ownership, and regenerating either golden to accept the leaked tools would mask what looks like a real registration-scope regression. Because `shipped-composition.e2e.ts:84` throws before its `EXPECTED_TOOLS` assertion at line 87 runs, whether that roster also needs the two outline tools once scoping is fixed is untested — unknown, not confirmed-fine. `apps/web/tests/pwsh-terminal.e2e.ts` fails separately with `duplicate loader entry id: tool-pwsh` (a loader/cordis-include defect, unrelated to timeouts or stale fixtures). `apps/web/tests/chat-scroll-contract.e2e.ts` fails on its own unscaled 10s `expect.poll` bound, already listed above (a Fork CI run on this PR showed it failing on two of its five tests, not one, at ambient load).
- A first Fork CI run on this PR's branch (32404094428) verified the fix's own targets: `pwsh-tool-turn` no longer appears among the failures. It also surfaced `examples/headless-agent/tests/headless.snapshot.ts`'s `keeps provider comments alive and sends DeepSeek defaults through the one-shot app` failing (`expect(server.requests).toHaveLength(1)` received 2) — a test that passed in the original failing run (32333218317) this change was scoped against, so this is new flakiness, not a regression this PR introduced through any file it touches. The doubled request count is consistent with an LLM-connection-layer retry (in `llm-deepseek`/`llm-retry`, neither owned by this change) firing under load, which would be a fourth, unscaled timeout-class bound distinct from vitest/harness timeouts — investigated only far enough to rule out this PR's diff as the cause; left to its own fix.
